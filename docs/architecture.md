# Architecture — Invoice & Accounts-Payable Document Intelligence Agent

This document explains how the blueprint is built and why: the graph, the split between code and model, the production data topology, the NVIDIA NIM deployment profiles, the guardrails, the checkpointed gate, and the path from this prototype to a production AP deployment.

> **Provenance.** The structural patterns in this blueprint — composable capability components behind narrow interfaces, NIM-first deployment profiles, an in-repo evaluation harness, guardrails enforced as code, run telemetry as a first-class output — follow the conventions of NVIDIA's published agent blueprints, which we treat as the reference playbook for how production agent systems are packaged. The implementation, documentation, policy corpus, and sample data in this repository are original work, written for this blueprint in the idiom of the Trida AI blueprint series. No code, prose, or assets are copied from NVIDIA repositories or any other source.

---

## 1. Problem framing

Accounts payable intake is high-volume, document-bound, and fraud-exposed. Before a finance approver can decide anything, someone must: read a scan of uncertain quality, verify it is an invoice at all, re-key its fields, compare every line against the purchase order and the goods receipt, check the tax arithmetic, look for a duplicate of an invoice already in the system, and decide which exception — if any — this is. Two failure modes matter more than all the others:

- **Paying twice** (duplicates) and **paying wrong** (price/quantity drift) — controlled by exact arithmetic, not judgement.
- **Payment-diversion fraud** — the "our bank account has changed" message, which arrives through exactly the channel this agent reads. Any automation that transcribes supplier text into payment instructions is an attack surface; this design treats that pattern as a first-class, separately-handled threat.

The design rule follows: **everything checkable is checked in code; the model is used for what it is good at (reading, summarising, drafting), and never for arithmetic, policy, or decisions.**

## 2. System shape

A LangGraph state machine runs one invoice through a fixed pipeline. Every external capability sits behind a port (a `typing.Protocol` in `ports.py`), and every port has an environment-selected implementation assembled in `wiring.py`. The graph never imports a vendor SDK.

```
                ┌──────────────────────────── FastAPI / CLI ───────────────────────────┐
                │  analyze · analyze/stream (SSE) · get · approve · reject · console     │
                └────────────────────────────────┬───────────────────────────────────────┘
                                                 │ InvoiceService
   ┌─────────────────────────────────────────────▼──────────────────────────────────────┐
   │ LangGraph pipeline                                                                  │
   │                                                                                     │
   │  ocr → vision → screen → extract → match → classify ─┬─ retrieve (policies)         │
   │                                                      ├─ discrepancies (code)        │
   │                                                      └─ history (store)             │
   │  → diagnose (bounded tool loop) → options (scored in code) → draft                  │
   │  → verify → review → validate (guardrails) → [bounded repair] → gate                │
   │  → approval_gate (interrupt) ⇢ resume on approver decision                          │
   └──────┬──────────┬──────────┬──────────┬──────────┬──────────┬───────────┬────────────┘
          │          │          │          │          │          │           │
     OcrEngine   DocVision  ModelBackend Retriever   Store   ObjectStore Checkpointer
       (NIM /      (NIM VL /  (NIM LLM /  (keyword /  (Postgres/ (S3 /      (Postgres /
        offline)    metadata)  Anthropic / semantic /  memory)   memory)     memory)
                               Ollama /    hybrid+
                               mock)       RRF)
```

Node order is deliberate. Screening runs before extraction and drafting so untrusted text is fenced or stripped before any model sees it. Matching runs before triage because triage consumes computed facts, not model impressions. The three fan-out nodes (retrieve, discrepancies, history) are independent reads over the same state. Verification, review, and validation are three separate mechanisms on purpose: a checklist (deterministic), a second model pass (judgement), and hard rules (code) fail differently, and a draft must survive all three.

## 3. Production data topology

There are no local files in the runtime story. One database is the system of record; one object store holds blobs; the application containers are stateless and interchangeable.

```
                        ┌────────────────────────┐
   approvers ──────────▶│  api (stateless, ×N)   │──────────┐
                        └──────┬──────────┬──────┘          │ approval
                               │          │                 ▼ webhook (opt-in)
              SQL (psycopg 3)  │          │  S3 API    AP system of record
                               ▼          ▼
                 ┌──────────────────┐  ┌──────────────────┐
                 │ PostgreSQL 16    │  │ Object storage   │
                 │ + pgvector       │  │ (S3 / MinIO)     │
                 │ ─ approvals      │  │ document blobs,  │
                 │ ─ checkpoints    │  │ keyed by         │
                 │ ─ policy vectors │  │ documents'       │
                 └──────────────────┘  │ object_key       │
                                       └──────────────────┘
                 ┌──────────────────┐
                 │ NVIDIA NIM       │  LLM · OCR · VL · embeddings
                 │ hosted or self-  │  (OpenAI-compatible endpoints)
                 │ hosted           │
                 └──────────────────┘
```

**Why PostgreSQL for everything.** The approvals store, the LangGraph checkpointer, and the policy vectors have the same operational profile — modest volume, strong consistency needs, one backup story. Splitting them across a database, a file store, and a separate vector service buys nothing at AP scale and triples the failure surface. pgvector keeps embeddings in the same transactions and the same backups as the records they describe; the corpus here is a dozen policies, and pgvector remains comfortable orders of magnitude beyond that. We chose it over a standalone vector database for one-database simplicity, and the `Retriever` port means that choice is reversible.

**Migrations, not ORM magic.** Schema lives in `migrations/` as numbered SQL files (`0001_core`, `0002_policy_embeddings`, `0003_checkpoints`), mirrored into the package (`src/ap_agent/migrations/`) so installed deployments run the same files the repo reviews — a test asserts the copies are identical. A tiny runner records applied versions in `schema_migrations` and applies pending files in order, one transaction each, when a Postgres-backed store or checkpointer is constructed. Production systems version their schema; this keeps that habit cheap.

**Object storage port.** Documents reference `object_key`s, not local paths. The OCR stage resolves a key through the `ObjectStore` port (boto3 against any S3-compatible endpoint; MinIO in compose) when a document carries no inline text. Unset `S3_BUCKET` disables the port and documents must carry their text layer — the hermetic default for tests and demos.

**Runtime posture.** Multi-stage Dockerfile (locked uv build, slim runtime, non-root user, healthcheck), `/health` for liveness and `/readiness` for store connectivity (503 when the database is unreachable, so an orchestrator stops routing), structured JSON logs with a per-request ID (`X-Request-ID` honoured inbound, returned outbound), configuration exclusively through environment variables, and graceful shutdown through the FastAPI lifespan. Batch analysis goes through the service layer, so concurrent workers share Postgres state exactly as in production — the duplicate sample behaves identically in a batch and in the API.

## 4. The NVIDIA NIM profiles

NIM services speak the OpenAI chat-completions dialect, so "built on NIM" is a configuration profile of the same provider seam rather than a fork of the engine:

| Capability | Port | NIM profile | Offline equivalent |
|---|---|---|---|
| Reasoning / extraction / drafting | `ModelBackend` (`openai`) | `OPENAI_BASE_URL=https://integrate.api.nvidia.com/v1`, `nvapi-` key, Nemotron model (e.g. `nvidia/nemotron-3-super-120b-a12b`) | deterministic templates (`mock`) |
| OCR | `OcrEngine` (`nim`) | `OCR_ENGINE=nim`, `OCR_MODEL=nvidia/nemotron-3-super-120b-a12b` | the document's provided text layer + confidence metadata |
| Document vision | `DocVision` (`nim`) | `VISION_ENGINE=nim`, a Nemotron VL model | deterministic verdict from provided metadata |
| Embeddings | `Retriever` (`semantic`/`hybrid`) | `OPENAI_EMBEDDING_MODEL=nvidia/nemotron-3-embed-1b` on the same endpoint | keyword retrieval |

Self-hosted NIM is the same profile with `*_BASE_URL` pointed at the containers (the local compose override documents the per-service URLs). Anthropic, plain OpenAI, and Ollama remain first-class `ModelBackend` choices — the engine is portable by construction.

**Adapter assumption (stated plainly).** The OCR NIM integration posts the document text to the endpoint's chat-completions shape and asks for a JSON reply of `{text, confidence}`. That request shape is an adapter seam: it isolates the one place that changes if a deployment's OCR service expects a dedicated document payload, and it is called out in the `ocr.py` docstring. Live NIM verification — hosted key against all four services — is a follow-up item; every NIM seam is covered by fake-based tests in the meantime.

## 5. The match, and why it is code

`matching.py` computes the three-way match exactly: per-line price variance (percent and absolute), quantity billed vs ordered vs received, line status in {matched, price_variance, quantity_variance, short_received, missing_on_po, missing_on_invoice, unmatched}, tax as stated vs implied-by-arithmetic, totals reconciliation, and currency consistency. Tolerances are constants with policy citations (AP-MATCH-01: price within 2% or 1.00, whichever is greater; totals within 1% or 1.00). Match status rolls up to {full_match, partial_match, no_match, no_po, no_receipt}; a line that corresponds but disagrees still counts as a partial match, reserving no_match for invoices whose lines do not correspond at all.

The match output is the single source of truth downstream: triage rules read it, the verify checklist requires every amount in a draft to come from it, and option scoring takes its match component from it. A model that "feels" the invoice matches cannot override arithmetic that says otherwise — the cross-check policy (next section) formalises the one narrow exception.

## 6. Triage and the cross-check policy

Rules classify first, from computed facts, with a fixed priority: not-an-invoice (vision) → unreadable → duplicate → missing PO → missing receipt → price variance → quantity variance → totals/tax/currency fallback → clean. Price outranks quantity when both occur (price is the money question). Fraud flags deliberately do **not** change the outcome — a clean-matching invoice with a bank-change request is a clean match under a fraud hold, and conflating the two would hide both facts.

When a provider backend is present, it independently classifies from the same facts, and `crosscheck.py` resolves the pair: agreement stands; if the rules are confident (≥ 0.85) they are authoritative over a disagreeing model; if the rules are weak and the model is confident (≥ 0.85) the model's outcome is adopted and the fact is recorded in the triage signals; with no usable model reply the run is rules-only. Every run's result carries the full cross-check record — both verdicts and the resolution — because "the AI said so" is not an audit trail.

## 7. Diagnosis with a bounded tool loop

Diagnosis is the one genuinely agentic step. A provider backend may call up to `DIAGNOSIS_MAX_TOOL_CALLS` tools (default 4, hard cap 6) — `search_policies`, `match_facts`, `supplier_history`, `po_lookup` — each returning computed facts, never new instructions. Every path degrades honestly: no tool support → single-shot LLM diagnosis; no usable reply → a template summary composed from the same facts, labelled `source: template`. Supplier history and prior approver feedback (recorded reject/approve reasons for the same supplier) are injected as evidence lines, which is how the feedback loop teaches later runs without any training.

## 8. Guardrails as code

`guardrails.py` validates the final draft pair; approval is refused (HTTP 422) for any run whose validation failed.

- `no_payment_language` — payment-made / payment-will-be-made assertions (with a negation window so the required disclaimer — "no payment is made or scheduled by this letter" — passes), plus any bank-content pattern: account numbers, sort codes, IBANs, "new bank account", remittance-to-account instructions.
- `no_prohibited_promises` — outcome guarantees and time commitments.
- `no_pii_in_draft` — SSN and Luhn-valid card patterns (invoice numbers and amounts must not trip it, and tests pin that).
- `policy_citations_present`, `references_invoice_id`, `states_next_step`.
- `citations_within_retrieved` — every policy a draft cites must be in the retrieved set; a plausible-but-unretrieved citation is invented authority.
- `figures_must_trace` — every currency amount the supplier letter states must trace to the verified fact block (the computed match registry: totals, line products, unit prices, tax, discount figures). The LLM-judge pack's last standing failure family was letters restating computed arithmetic in prose and drifting (a subtotal of 1000.00 against a computed 1070.00); the rule is that figures live in structured fields and the packet's tables, and the letter refers to them. The packet is exempt — it prints the computed figures directly. The drafting prompt carries the same discipline, plus quantity wording: the goods receipt records the *received* quantity, never "delivered".

The bank-change defence is layered, deliberately: screening flags the pattern and blocks the approve option + autonomy; sanitisation strips the sentences from prompts; flags carry digit-masked excerpts and draft-safe labels; the diagnosis carries the label, never the sentence; and the guardrail rejects any draft in which bank content survived anyway. INV-1010 exercises every layer. INV-1012 is the complementary trap: a supplier note relaying a payment-date demand is *not* an injection (the screen correctly leaves reported speech alone) — it is the drafter's job not to repeat it, and the guardrail's job to catch it when the drafter does.

The screen also checks stated details against **supplier master data** (the `SupplierMaster` port, `supplier_master.py`): bank identifiers extracted from bank-context sentences are compared with the approved master record (PostgreSQL, migration 0008; in-memory double offline). A mismatch is itself the fraud signal and blocks; a match is evidence — a pattern hit whose details are the ones already on file is downgraded, because the "change" pointed at the approved account. Where no master record exists the screen keeps its pattern-only behaviour, and the verdict (`checked_match` / `checked_mismatch` / `no_master_record` / `no_details_in_documents`) rides on the result with masked labels only.

A failing draft enters a bounded repair loop (redraft with the failures named, up to `GUARDRAIL_REPAIR_MAX_ATTEMPTS`); the original failure stays on the record either way.

## 9. The gate, checkpoints, and autonomy

The graph ends in an interrupt: the run pauses at `approval_gate` with its full state in the checkpointer (Postgres saver over psycopg 3, mirroring the reference saver semantics — the pinned LangGraph ships base and in-memory savers only, so the saver is implemented against the existing port; an integration test pauses on one saver instance and resumes on another to prove restart survival). The service records the decision in the store (the system of record — graph threads are workflow state, not the ledger), then resumes the thread to completion. Approving requires the run's guardrail validation to have passed.

The autonomy recommendation is computed, printed, and never acted on: eligible only for `clean_match`, low severity, `full_match`, at or under the approval threshold, no fraud flags, validation green, no repair, an agreeing cross-check, and an unblocked reviewer. Its purpose is to make the automation roadmap discussable with data instead of vibes.

The approval webhook (`ACTION_WEBHOOK_URL`) is the single external action in the system, opt-in, fired after a human decision — it announces that a packet was approved; it does not pay anything. When `ACTION_WEBHOOK_SECRET` is set, the body is HMAC-SHA256 signed (`X-Trida-Signature: sha256=<hex>`) so the receiving system can verify origin and integrity before acting on it.

## 10. Observability and cost control

Every run returns telemetry: backend, model, call count, token usage, estimated cost (a small price table; models outside it — including Nemotron — report `None`, shown as n/a, never invented), latency, and per-node timings via the event sink (the API's SSE stream is the same events). `RUN_TOKEN_BUDGET` wraps the backend in a guard that, once the budget is spent, hides the optional provider capabilities so later steps degrade to their deterministic paths instead of failing mid-run — the run completes, labelled honestly.

Structured JSON logging with request IDs threads the API surface; the CLI's `--stream` flag prints the same event stream for a local run. Two read surfaces aggregate the store itself: `GET /metrics` (runs, outcomes, decisions, mean latency, token/cost totals summed only over runs that reported them — null, not zero, when none did) and `GET /audit/export` (JSON/CSV: one row per invoice with the triage conclusion, the human decision and its reason, and the dispatch outcome). Aggregating at read time keeps the store the single source of truth — there is no counters table to drift.

## 11. Evaluation

Two packs, both in-repo. The deterministic pack (`evals/run_evals.py`) runs 30 golden cases — the 14 samples plus 16 constructed variants — through one service instance in queue order (order is load-bearing for the duplicate case) and gates on triage-outcome and match-status accuracy at 95%; it then matches the bundled sample credit notes against the populated store, so a note can only settle a variance its invoice actually computed, and drafts the duplicate-recovery pack for the portal-resend sample once its original is approved. The opt-in LLM pack (`evals/run_llm_evals.py`) runs the same cases against a live provider and adds an LLM judge for draft grounding and cleanliness; it exits 2 without a provider rather than grade the offline templates. Neither pack claims real-world accuracy: the golden set is synthetic and exists as a regression gate.

## 12. Testing posture

The pytest suite (401 tests) is hermetic: in-memory doubles for the store, checkpointer, and object store; scripted fake backends for the provider seams; fake NIM engines for the OCR/vision ports. Test doubles are test design, not a runtime mode — the documented runtime stores are Postgres and S3. Postgres behaviour is covered by integration tests gated on `DATABASE_URL` (store round-trip, checkpointer pause/resume across instances, pgvector retrieval with a stubbed embeddings client) that skip cleanly when no database is configured.

## 13. Follow-on AP work: discounts, credit notes, statements

Three surfaces operate over the processed queue rather than a single run, all with the same discipline — code computes, humans decide, nothing external happens:

- **Early-payment discounts** (`discounts.py`) are priced inside the run: terms are parsed from the intake (`payment_terms` field or a document field), the gross saving is compared against the cost of paying early at the configured cost of capital, and a worthwhile net saving enters the approve option's score (capped) and is quantified in the packet. The deadline is stated as a condition — the payment-language guardrail rejected an earlier "paid by" phrasing, correctly, and the packet wording was changed rather than the guardrail.
- **Credit-note matching** (`creditnotes.py`) answers "does this credit settle a variance we computed?" from stored match facts: overbilling is recomposed per line (price, quantity, short receipt, missing-on-PO) and grossed at the invoice's effective tax rate, so the comparison is tax-inclusive like the credit itself. It is a query: no invoice state changes.
- **Statement reconciliation** (`reconciliation.py`) lines a supplier statement up against the store's history projection. Its summary is composed deterministically (`summary_source: template`) by design: on this surface a plain summary beats a fluent one that might invent a figure. Reports persist (migration 0004) for human confirmation; confirmation touches the report only.
- **Payment runs** (`paymentruns.py`) close the loop the gate opens: approved invoices are grouped by currency and due window — windows anchored on the proposal date, overdue swept into the first — with gross, discount, and net totals summed in code. The discount column reuses each run's stored evaluation and counts only while its deadline is still reachable. A run persists (migration 0005) as a draft object; a finance lead's confirmation is recorded on the run, members of a confirmed run leave the proposal pool, and no invoice record is touched either way. The proposal is the deliverable — execution belongs to the AP system of record, exactly like the approval webhook's packet.
- **The aging queue** (`queue.py`) is a read model, not a workflow: awaiting invoices aged against due dates into the conventional buckets, ordered most-overdue first, with the triage mix and per-currency totals. It exists because the approver's real question is workload-shaped ("what is late?"), and because a read model over the record can never drift from it.
- **Recovery packs** (`recovery.py`) handle the sequence the duplicate control cannot prevent: the original was approved *before* the duplicate arrived. The pack's evidence is computed from both records (identity of supplier/number/amount, both submissions, the exposure — one payment in flight or two), and its two drafts reuse the pipeline's own verification and guardrail functions rather than a parallel checker, so a recovery letter is held to the same no-payment-language, citation, and grounding rules as any draft the agent writes. Packs persist (migration 0006); sending and chasing stay human work.
- **Bundles** (`bundles.py`) move a real intake shape — one scan, many invoices — into the same per-invoice pipeline without a batch-shaped fork in the graph: segmentation and segment parsing are deterministic (anchors, line grammar, PO mapping by description), and from the segment onward there is only the ordinary run. Bundle summaries persist (migration 0007) so an arrival can be audited as a batch while its invoices are decided one by one.
- **Payment-run hand-off** (`handoff.py`) completes the run story: a confirmed run renders as a bank-ready file and is stored through the object-store port. Two serializations sit behind the one seam — the CSV (layout v2 — header row, one row per line, totals row, creditor columns appended) and an ISO 20022 pain.001.001.09 credit-transfer document (one `PmtInf` for the run, one transaction per line at its export-time net) — under the same gates (confirmed, four-eyes where stamped, drift re-verified at export), with the element-by-element mapping in `docs/handoff-formats.md`. The renderers are pure, so the sha256 recorded on the run is a stable content hash. The file is the routing adapter to the customer's banking/ERP system; generating it changes no payment state, and a human carries it the last mile.
- **Recovery-case lifecycle** (on `recovery.py` packs): a drafted pack opens a case (`opened → supplier_contacted → credit_received → closed`) that operators walk one step at a time through the service/API/console, every transition appended to the pack's audit history with actor, timestamp, and note. Skips and backwards moves are refused; a guardrail-blocked pack cannot be walked, because its letter may not be sent. The agent records the case — contacting the supplier and banking the credit remain human work.
- **ERP posting example** (`examples/erp_posting.py`) demonstrates the output seam for pull/import flows: an approved result's JSON becomes a generic double-entry journal (purchases / input tax / AP control) with a stable idempotency key. Amounts come from the computed facts, unapproved results and unreconciled figures are refused, and there is deliberately no vendor SDK or network — the transport into a real ERP is the customer's step.
- **Governed master changes** (`master_changes.py`, migration 0009) close the hole the master-backed screen opens: if the screen trusts the master, the master's change path must be at least as governed as the payments it protects. A change is a stored request object — proposed by an operator, or from a document (the identifiers an invoice's text states, extracted exactly as the screen extracts them and overlaid on the current record) — and it applies only after a *second* operator approves it with the out-of-band verification reference recorded, and its effective date arrives. Promotion is a sweep (`apply_due_master_changes`, run at the top of every analysis and exposed to operators), so screening always compares against the record in force today. Until a change is approved and in force, documents stating the new details keep returning `checked_mismatch` — a pending change is not a fact, and the workflow never lets a document update the record it is checked against.
- **Four-eyes on payment runs** (on `paymentruns.py` runs): the invoice gate has an approval threshold, and runs get the same treatment at run scale — a net total above `PAYMENT_RUN_FOUR_EYES_THRESHOLD` stamps the run at proposal time, and the hand-off export refuses it until a second confirmer, different from the first, has confirmed it too. Stamping at proposal (not evaluating at export) keeps the rule stable for a stored run even if the configuration later changes; the boundary is strict (at the threshold is not above it), and both confirmers are named on the run record.
- **Recovery-case aging** (in `queue.py`): the case lifecycle made stalls visible only one case at a time, so the queue and `/metrics` now age every open case — total age, age of the current status, buckets, and an SLA breach flag past `RECOVERY_CASE_SLA_DAYS`. The SLA deliberately runs on *status* age rather than total age: it measures stuck-ness, and a case that transitioned yesterday is being worked however old it is.
- **Posting receipts** (on the invoice record): the ERP example's return path. The ERP's outcome is recorded through a service stub (`record_posting_receipt`) shaped by the example's `build_receipt` — `posted` with the ERP document number or `failed` with its reason, tied to the posting by its idempotency key, and visible in the audit export. The integrity rules mirror the posting side: only approved invoices carry receipts, a posted receipt replays by key but refuses replacement by a different posting (double-posting is corrected in the ERP, not here), and a failed receipt may be superseded by its retry. The loop closes without the agent posting anything itself.
- **Discount drift at export** (in `paymentruns.py`): the discount column is priced at proposal time ("counts only while its deadline is still reachable" — reachable *then*). Confirmation and export can be days apart, so export re-runs the pricing (`discount_drift`) over the stored invoices as of the export date. The rule is deliberately not "refuse": the clean members' payments should not wait on one member's lapsed window, and paying the stale net would short-pay the supplier — once the window closes, the full gross is what is owed. So the drifted member is exported at full gross, the exported figures become the run's figures, and `handoff_drift` itemises what was confirmed, what survived, and what was lost. Drift is priced, flagged, and paid correctly — never silent.
- **Master coverage** (in `supplier_master.py`, surfaced in `/metrics`): a control that only works where data exists should publish its own coverage. The metric counts, over the processed invoices, how many suppliers have a master record (by invoice count and by spend), the recorded verdict mix, and the pending changes in flight. It also keeps the workflow honest: a pending change is reported as in flight, never as coverage — the gap closes at application, not at proposal.
- **Master-change expiry** (in `master_changes.py`): the governed change path had a waiting room with no clock. A pending request is a live credential change; past `MASTER_CHANGE_EXPIRY_DAYS` it expires — the sweep mirrors the promotion sweep (same call sites, plus an operator endpoint), a decision attempted after the window performs the expiry itself rather than deciding a stale request, and the expiry is an audit-history event with actor `system`. Expiry refuses nothing legitimate: the proposer re-proposes in one step, and fresh eyes on a fresh request is precisely the control.
- **Approved-not-posted reconciliation** (`posting.py`): the receipt loop's complement. Receipts close the loop when they arrive; this read model reports the approvals they never arrived for — no receipt, or only a failed one — past `POSTING_RECEIPT_GRACE_DAYS`. It reuses the decisions the service now timestamps (`decided_at` on the result, with a labelled submission-date fallback for older records) and the same read-model discipline as the queue: computed from the store at read time, ordered oldest first, writing nothing. A failed receipt keeps its item open with the ERP's reason attached, because a refused posting that nobody retried is the same open loop as one never attempted.
- **pain.001 hand-off** (in `handoff.py`): banks and many ERPs ingest ISO 20022, not CSV, so the hand-off seam gained a second serializer rather than a second workflow. The pain.001.001.09 document maps the run one-to-one (mapping table in `docs/handoff-formats.md`) and sits behind the identical gates — confirmed, four-eyes, drift re-verified — because the format is a rendering choice, not a trust choice. The bank-account elements are handled by provenance: the file never sources account data from documents (documents are what the fraud screen checks *against* the master), the debtor account is the customer's bank-portal data and always carries its `*-AT-IMPORT` marker, and the creditor account is completed at export from the governed master where it holds approved details — see **Creditor-account completion** below — keeping its marker everywhere else. An import that rejects the markers is the control working: the gap is visible at the step where the authoritative data lives.
- **Duplicate screening across arrival shapes** (in `store.py` + `reconciliation.py`): the duplicate control compared raw strings, which made its verdict depend on the arrival shape — a portal form writes `NB-4471`, a bundle's segment text and a statement line write it differently again, and supplier names vary in case and punctuation. Identity is now a canonical key (`duplicate_key`: supplier punctuation dropped, case folded; number reduced to alphanumerics), used by the intake check in both directions (segment-after-single and single-after-segment, twins named either way) and by statement reconciliation, which additionally flags numbers AP holds twice and numbers the statement itself repeats. The screen only flags — the gate and the recovery path take it from there, unchanged.
- **Drift-value and export-lag metrics** (`paymentruns.handoff_metrics`): per-run drift was an anecdote; aggregated, it is a process measure. `/metrics` now totals the discount value drift destroyed per currency and reports the confirm→export and proposal→export lag distributions beside it — the lag is the leak that causes the drift, and AP cannot fix a process it cannot see. Legacy runs without receipt stamps are excluded from the lag stats rather than averaged in as zeros.
- **Open-posting escalation** (in `queue.py`, threshold in the service): the approved-not-posted report made open items visible, but a report is easy to not read. Past `POSTING_ESCALATION_DAYS` — a second threshold, clamped so it can never sit below the grace window — an open posting joins the approver queue as an action item with its ERP failure reason attached, and `/metrics` counts the escalations. The queue stays a pure read model; escalation is a threshold on the same computation, not a new state on the invoice.
- **Recovery-case escalation webhook** (in the service): the recovery aging had the same pull-only flaw — a breached SLA sat in the queue until someone looked. A sweep (`escalate_breached_recovery_cases`, `POST /recovery-cases/escalate`) fires the signed `recovery_escalation` webhook over the same opt-in seam and HMAC scheme as the approval dispatch, carrying the case's aging snapshot. The dispatch is ledgered on the pack itself (`escalations`), deduped by (case status, status start date): once per crossing, and a case that moves and stalls again earns a new one. The ledger deliberately lives outside `case_history` — the status-age clock runs from the last history event, so an escalation entry there would reset the very age it reports. With no webhook configured the sweep records nothing: there is no dispatch to dedupe against.
- **Per-currency four-eyes thresholds** (in `paymentruns.py` + the service): the four-eyes gate was one global number, but 25,000 USD and 25,000 JPY are not the same risk. `PAYMENT_RUN_FOUR_EYES_THRESHOLDS` maps currencies to their own figures with the global threshold as fallback (in both directions — a currency figure can tighten or relax its gate), and the figure that applied is stamped on the run at proposal (`four_eyes_threshold`), named in its note, and quoted in the second-confirmation and export refusals. Stamping keeps a stored run's gate stable under later configuration changes, as with the original rule.
- **Creditor-account completion** (in `handoff.py`): the creditor account was the hand-off's one deliberate marker the system could honestly fill. At export, each member's supplier is resolved against the governed master, and where — only where — the master holds approved bank details, the file emits them (IBAN as the `IBAN` element, else the account number with the sort code as creditor agent; the CSV gains the account and its source as layout v2). The debtor side keeps its markers always: it is the customer's own account, not master data. The export receipt (`handoff_creditor_entries`) records completed vs marked per member with masked labels only — the full identifiers live in the master and in the file, never on the run record.
- **Drift forecasting at confirmation** (in `paymentruns.py`): drift was measured at export and aggregated in metrics — always after the money was lost. Confirmation now projects the same numbers forward: the expected export date is the run's proposal date plus the measured mean proposal→export lag, and discounted members whose deadlines fall before it are flagged (`drift_forecast`, with `drift_forecast_basis` stating the lag or the honest absence of one). The forecast is labelled as a projection in the data, the run note, and the console; it changes no figures, and the export-time re-pricing remains the authority on what actually lapsed.
- **Forecast accuracy** (in `paymentruns.py`, surfaced in `/metrics`): a projection that is never graded is a decoration, so every exported run's flags are now set against its measured drift — flagged & drifted, flagged & saved, unflagged & drifted, unflagged & saved — with precision, recall, and the value on each side, overall and per currency. The scoring is deliberately honest about its edges: a flagged-and-saved member credits the warning without claiming the warning *caused* the save, and runs whose confirmation made no forecast (no measured lag existed, or the export predates forecasts) are unscored — their drift is reported separately instead of poisoning the recall denominator with misses nobody could have flagged.
- **Creditor-completion coverage** (in `paymentruns.py`, surfaced in `/metrics`): master coverage counts records, but what reaches the bank is exports. This metric reads each exported run's completion receipt (`handoff_creditor_entries`) and reports, per currency and per hand-off format, the share of exported members and of exported value completed from the master versus still carrying the at-import marker — the residual import risk, priced. Values are the export-time net figures the bank was told to pay; receipt-less legacy exports are counted as such, so coverage never quietly improves by shrinking its denominator.
- **Four-eyes aging** (in `queue.py`, threshold in the service): the four-eyes gate created a new stall shape — a run confirmed once, hand-off locked, waiting on a second confirmer who may not know they are being waited on. Past `PAYMENT_RUN_FOUR_EYES_AGING_DAYS` (default 2) the run joins the queue as an action item carrying the run, its net total, the wait's age, and the first confirmer's name: the person to nudge, and — by the four-eyes rule itself — the one person who cannot resolve it. Like the posting escalation, it is a threshold on a read model, not a new state on the run.
- **Escalation digest** (`digest.py`, `GET /digest`): the queue is a pull surface and the webhooks are a machine channel; the digest is the human-readable push counterpart, with the agent's usual restraint — it composes and sends nothing. For a day it gathers the queue's action items (recovery breaches with the amounts at risk, escalated postings, overdue gate items, four-eyes stalls) and the day's run news (forecast lapses on runs confirmed that day, drift realised on runs exported that day) into one summary in the reconciliation summary's discipline: computed, every exception named, an explicit all-clear on a quiet day. A customer's scheduler can poll the endpoint; a human forwards the text. Either way the sending, if any, is not the agent's.
- **Stored digests** (migration 0010, store pair like reconciliations): a computed digest is a function of the records *now*, so it cannot answer for yesterday once the records move — the digest a human forwarded on Friday is unrecoverable on Monday, because the cases transitioned over the weekend. Storing is therefore an operator action (`store_digest`, `POST /digest/{date}/store`) that pins the day's first-computed digest with the storer's name and the storage time, provenance `stored`. First-computed wins for the same reason the recovery ledger dedupes: the copy that may already have been forwarded is the record, and a later recomputation silently replacing it would falsify the audit file. Recomputation stays available and is labelled `computed` — the label is the honesty mechanism, not a warning. The stored series (`digest.build_digest_history`, `GET /digest/history`) reduces each day to its headline counts with the changes against the previous *stored* day: gaps are the operator's storage discipline made visible, never interpolated away.
- **Marker-risk worklist** (`worklist.py`, `GET /suppliers/marker-worklist`): completion coverage prices the at-import marker over exports; a price does not assign work. The worklist reads the same completion receipts and ranks suppliers by marked export value at export-time net — per (supplier, currency), because a ranking that compares raw values across currencies would sort by exchange rate, not by risk. Each row carries the marked invoice count and ids and the last marked export date: the fraud screen's blind spot as an owned queue. Resolution is checked against the live master with the export completion's own has-details rule (a record exists *and* carries an IBAN or account number — a name-only record completes nothing, so it resolves nothing), and resolved suppliers stay counted with their formerly-marked value: a worklist that silently shrinks teaches nobody that onboarding worked. The console's one click prefills the governed master-change form; the worklist itself onboards nobody.
- **Forecast-aware four-eyes aging** (in `queue.py`): the four-eyes aging threshold was a single configured patience, but patience is only free when nothing decays during it. A run whose confirmation-time forecast flags lapses cannot export until its second confirmation lands, so for that run the wait *is* the drift mechanism the forecast predicted — its threshold therefore tightens to 0 days (`FORECAST_TIGHTENED_AGING_DAYS`) and it joins the queue on the first day of the wait, carrying the lapse count and projected value at risk, sorted ahead of older untightened waits because value at risk outranks raw age. Two disciplines hold: the forecast is read exactly as stamped at confirmation (the queue recomputes nothing — a read model that re-derives its inputs can drift from the record it describes), and an empty forecast changes nothing, so the configured threshold remains the rule the forecast must earn its way out of. The digest's forecast section marks lapses on unseconded runs `blocked_on_four_eyes`, so the projection names its own blocker.
- **Open-posting escalation webhook** (in the service): the open-posting escalation had the same pull-only flaw the recovery escalation fixed — a crossed threshold sat in the queue and the digest until someone looked. The sweep (`escalate_open_postings`, `POST /postings/escalate`) fires the signed `posting_escalation` event over the approval channel's seam and HMAC scheme, carrying the posting's snapshot rather than any document content. The ledger placement differs from the recovery packs' on purpose: a posting's life lives on the invoice record, so its ledger sits there too, beside the receipt fields it escalates against. Dedupe is per *episode* — (receipt state, episode start) — because the postings' clock has two honest starts: the approval, and a failed receipt, which is new information (the ERP refused; someone must retry or reroute) and earns one escalation of its own when its episode crosses. A posted receipt is the reset: it closes the item, and no ledger entry can resurrect it. `/metrics` counts recorded pushes beside items past the line, keeping the two numbers — crossings seen, crossings announced — separately auditable.
- **Worklist flow state** (in `worklist.py`): the marker worklist ranked exposure but could not say whether anyone was already working a row — the failure mode is two operators proposing two changes for one supplier while a third change sits undecided. The worklist now joins the store's master-change requests (latest per supplier, expiry evaluated with the same `master_changes` rules the workflow itself uses) and stamps each row with its flow state: `in_flight` for a live change (pending inside its decision window, or approved awaiting its effective date), carrying the change id, proposer, and age — the decision is owed by a *second* operator, and the row says who proposed so it also says who may not decide; `rejected` with the decider, date, and recorded note, so the refusal is part of the work item; `open` otherwise, with an expired pending change honestly back to open. The join stays pure and the service supplies the inputs, exactly like the resolution check beside it.
- **Posting-escalation ladder** (in the service): the escalation webhook fired once per episode and then stayed silent however long the posting stayed open — a paging system that gives up after one page. The sweep now climbs two rungs: `posting_escalation` past the threshold, `posting_escalation_urgent` past twice it, the second payload naming its rung so one receiver can route them differently. The ledger discipline extends rather than changes: dedupe is per (receipt state, episode start, *level*), a posted receipt remains the only reset, and a sweep climbs at most one rung per posting — a posting first *seen* past the second threshold hears level 1 first and level 2 on the next sweep, so the receiver's log shows an escalation story, not a simultaneous pair. `/metrics` splits recorded pushes by rung: crossings announced, and crossings that needed the second shout, stay separately auditable.
- **Digest auto-store sweep** (in the service): stored digests fixed the record's permanence but left its *completeness* to a morning ritual — the history's gaps were, in the round-10 wording, "the operator's storage discipline made visible", which is another way of saying the trend breaks exactly when the team is busiest. The sweep (`store_due_digests`, `POST /digest/store-due`) walks a bounded lookback (`DIGEST_STORE_LOOKBACK_DAYS`, default 7) oldest-first and stores each unstored day through the identical `store_digest` path, so first-computed still wins and a human-stored day is reported `already_stored`, never overwritten. The provenance carries the honesty: sweep-stored copies are attributed to `system` with the real storage timestamp, because a digest computed today and aged to Tuesday is a backfill, not a Tuesday-morning observation — the label says which. The lookback is bounded on purpose: the sweep exists to forgive a forgotten week, not to manufacture a year.
- **Priced four-eyes wait** (in `paymentruns.py`): four-eyes runs had their waits measured three ways — aging thresholds, forecast-tightened queue entries, digest flags — and priced none of them, while drift priced a *different* span (confirmation to export, whatever caused it). `price_four_eyes_wait` isolates the wait itself: a member discount is charged to the wait exactly when its deadline falls inside it — capturable on the first confirmation's date, gone by the second's — under the same capturable-on-the-deadline-day rule as the proposal and the drift check. The attribution edges are the design: a discount that died before the first confirmation is charged to nobody here (drift still prices the whole span), and one alive at the second confirmation cost the wait nothing, so the number cannot be inflated by the calendar or by a fast second confirmer. The stamp lands on the run at second-confirmation time (`four_eyes_wait_lapses`, `four_eyes_wait_cost`) and aggregates in `/metrics` beside the forecast accuracy — the control's measured cost, finally on the same page as the losses it exists to prevent. It changes no figures: export re-pricing remains the authority on what is paid.
- **Hand-off routing profiles** (`handoff_profiles.py`, migration 0011): the export chose its format per call, which put a payee-side fact — what the receiving bank or ERP actually ingests — in the hands of whoever happened to click Export. The profile moves that knowledge into governed configuration: one record per supplier or per currency (deterministic id, so re-setting updates rather than forks), carrying the preferred format, a lead-days figure, and the marker-rejection stance, with the actor named and an append-only audit trail inside the record. Resolution (`resolve_export_format`) is a stated precedence, not a negotiation: an explicit format on the call outranks configuration (the human at the keyboard wins), then the currency profile (the ERP target is the stronger fact — it is where the file is going), then supplier profiles only in unison — a run is one file, so two profiled members pointing at different routing values are split voices and no supplier profile governs. The lead-days rule (`requested_execution_date`) is asymmetric on purpose: it takes the *later* of the window end and export + lead, so lead time buys a slow bank its runway and can never pull a payment ahead of the last due date in the window. And the marker stance is consumed at proposal time, not export time — flagging a member whose bank refuses markers while the master cannot complete it, on the run, where the remedy (onboard the supplier) is still cheap. The profile changes no run by itself; it is read exactly twice, at proposal and at export, which keeps its blast radius auditable.
- **Wait-cost budgets** (in `paymentruns.py`, surfaced by the service): pricing the four-eyes wait (above) produced a number with no owner — it could grow every month and nobody's threshold would ever trip. The budget gives the number a ceiling per currency (`FOUR_EYES_WAIT_BUDGETS`, parsed with the same CODE=amount discipline as the four-eyes thresholds it sits beside): `wait_cost_budget_status` charges each run's priced wait to the month its second confirmation landed — the moment the wait ended and the cost became final, rather than the proposal month the run happened to start in — and reports cost, ceiling, and excess side by side. Two honesty rules carry the design: exactly-at-budget is not over (a ceiling is a limit, not a target to undershoot), and an unconfigured currency reports `budget: null` rather than breaching against an invented zero — absent governance is stated as absent. The surfaces split by cadence: `/metrics` owns the current month's table; the digest, a daily surface, carries only the breach, and carries it every morning until the month turns — a monthly fact that stops being said the day after it trips would be a rumour, not a control.
- **Worklist expiry early warning** (in `worklist.py`): the flow state (above) told the worklist a change was in flight and how old it was, but age alone does not say *urgency* — a 26-day-old change is calm under a 90-day window and nearly dead under the default 30. The row now carries the remainder (`in_flight_days_to_expiry` = window − age, computed with the same `master_changes` age/expiry functions the workflow itself enforces, so the warning can never disagree with the eventual expiry) and the warning band is a configuration (`MASTER_CHANGE_EXPIRY_WARNING_DAYS`, default 7), not a constant buried in a read model. The boundary semantics inherit the workflow's: on the window's last day the change is still decidable, so days-left 0 warns rather than disappears — the warning's whole purpose is the last rescueable days. Approved changes are deliberately excluded: decided work does not expire, and warning about it would train operators to ignore the flag. The digest repeats the warning with the marked value attached, because "a change is expiring" is trivia and "EUR 40,000 keeps exporting marked if this change dies" is a decision.
- **Digest-store coverage** (in `digest.py`): the digest series became the audit file, and the sweep (above) made it nearly complete — nearly being the word an auditor will lean on. `digest_store_coverage` turns the store's completeness into reported facts: stored days by attribution (a morning ritual, a `system` backfill, and an honest `unattributed` bucket for legacy copies, because guessing a provenance would corrupt the very record being audited), the stored range's bounds, and the gaps *inside* the range — the range's edges are not gaps, since the series legitimately starts and ends somewhere. The split that matters is recoverability, computed against the sweep's actual reach (anchor − lookback + 1): a gap inside the reach is a chore (run the sweep), a gap before it is a permanent hole, and reporting both kinds under one count would hide exactly the distinction the audit exists to draw. It lives in `/metrics` beside the other store-health numbers rather than in the history view: the history is the evidence, the coverage is the evidence's chain of custody.
- **Drafting that survives a live model** (in `graph.py`, `prompts.py`, `guardrails.py`): a live Nemotron run exposed two drafting flaws the offline templates never had — the packet draft dropped the policies the diagnosis cited (the independent reviewer blocked it; the spine working as designed), and the letter's next step drifted into prose, with a repair loop told only that validation failed. The drafting path now composes deterministically where it must: the packet carries the diagnosis's retrieved policies appended in code when the model drops them (retrieved-only, so the citations guardrail still polices every bracket), the letter prompt names the `Next step:` line as a required line, and every failed guardrail check reaches the repair beside its per-check fix directive — in the repair prompt and in the model's correction block alike. The offline template path is byte-stable and never repairs; no guardrail or reviewer standard was loosened to make a live draft pass.
- **The duplicate screen, read back as a graph** (in `twins.py`): the duplicate screen fires per arriving record, but a resubmission campaign is only visible whole. `twin_clusters` unions records over the duplicate-of edges the screen recorded plus shared canonical-key/total evidence, and the audit export carries the cluster per row (`duplicate_of`, the arrival shapes on both sides of the edge, cluster id and size) with `GET /audit/twins` returning the clusters themselves. Arrival shape is stamped at analysis time (`single` vs `bundle_segment`) — a duplicate that arrived re-cut out of a remittance bundle is a different operational fact from a re-upload, and the graph says which.
- **Batch booking, and the lead rule stated per group** (in `handoff.py`): a governing profile's `batch_booking` groups a pain.001 export into one `PmtInf` per requested execution date for banks that book per value date. The interaction with lead days is explicit, not emergent: a line's group date is the later of its due date (window end when it has none) and the profile's lead floor — the floor buys the bank its processing time on every group, and no group executes before its lines fall due. Completion entries carry the execution date their member exported under, so creditor-completion coverage splits by PmtInf grouping; the default render stays byte-identical under its golden file.
- **Profiles, graded** (in `handoff_profiles.py`): stamps exist to be read back. `profile_effectiveness` grades each profile over its governed exports — routed count and format mix, member/value marker rates beside the ungoverned population's, follow-through on the suppliers its rejection stance flagged at proposal time, and lead promises checked against the dates actually written (every date of a batch stamp counts). The notes name the failure modes plainly: governing nothing, governing no safer than nothing, a flag that did not stop the marker, a breached lead. Grading configuration is what keeps governed configuration honest.

## 14. From prototype to production

What changes for a real AP deployment, in rough order: SSO + role-based access on the gate itself (the separation-of-duties rules already exist where the money moves — proposer ≠ approver on master changes, four-eyes on large runs — and become identity-backed rather than name-based); an ERP/AP-system integration behind the webhook (the packet becomes a posting, still human-triggered, with the receipt loop already shaped to receive its answer); document ingestion from the mailroom/scanner pipeline writing blobs to object storage; per-entity policy corpora replacing the synthetic 12; NIM self-hosting or hosted-key management in the platform's secret store; and the LLM-judge pack running in CI against recorded provider budgets. What does not change: the ports, the match arithmetic, the guardrails, or the rule that the agent prepares and a human decides.
